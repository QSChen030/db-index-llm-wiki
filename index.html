單元一：為什麼需要索引？

沒有索引時，資料庫只能「全表掃描」

💡 生活化比喻：沒有目錄的 1,000 頁厚字典 想像你要在一本沒有目錄的字典裡找一個生字，你只能從第 1 頁一頁一頁往後翻，最壞的情況必須把整本 1,000 頁全部翻完才能確定找不找得到。
🐢

全表掃描（Full Table Scan）

  • 資料庫被迫從第一筆資料逐行讀取比對，時間複雜度為 O(N)。
  • 必須將硬碟上所有資料頁（Page）載入記憶體，產生極高的 Disk I/O 成本。
🚀

建立索引（Index）之後

  • 為特定欄位建立獨立的排序目錄結構，時間複雜度降至 O(log N)。
  • 只需讀取極少數索引頁就能直接跳轉到目標資料位置。
概念 1 / 4：I/O 成本基礎 資料來源：wiki/01_full_table_scan.md
單元二：核心資料結構

B+ Tree 如何用 3 層結構管理千萬筆資料？

💡 生活化比喻：部首檢索表 → 筆畫索引 → 實際頁碼 查字典時，先看部首表（第 1 層），再看筆畫頁（第 2 層），最後直接翻到正文（第 3 層），只需 3 個動作就能精準定位。
1. 根節點（只存鍵值與指標）
➔
2. 內部節點（快速縮小範圍）
➔
3. 葉子節點（雙向相連＋資料指標）

為什麼樹這麼矮（僅 3 層）？

非葉子節點不存完整資料列，只存索引鍵值與指標，讓單一磁碟頁能塞入上千個分支指標。

為什麼葉子節點要串起來？

最底層的葉子節點之間有雙向指標相連，查詢區間（如 BETWEEN 20 AND 30）時不用重新從頭找。

概念 2 / 4：B+ Tree 結構 資料來源：wiki/02_b_plus_tree.md
單元三：儲存與回表機制

聚集索引 vs. 非聚集索引（什麼是回表查詢？）

比較維度 聚集索引（Clustered Index） 非聚集索引（Non-clustered Index）
生活化比喻 字典正文直接按拼音排序，找到就看到解釋 書末關鍵字表，先查到「頁碼」再翻回正文
葉子節點內容 直接存放完整的一整列資料 只存放索引欄位值 ＋ 主鍵（Primary Key）
數量限制 每張表只能有 1 個（通常為主鍵） 每張表可以建立多個（依查詢需求）
查詢次數 查 1 棵樹直接拿到所有欄位 若需其他欄位，必須拿主鍵再查一次（回表查詢）
概念 3 / 4：索引儲存差異 資料來源：wiki/03_clustered_vs_nonclustered.md
單元四：多欄位組合技巧

複合索引與「最左前綴原則」

💡 生活化比喻：先按「姓氏」、再按「名字」排序的電話簿 如果你只知道對方「姓陳」，可以快速翻到陳姓專區；但如果你只知道名字叫「卿順」卻不知道姓什麼，整本電話簿的排序就完全派不上用場。
✅

有效命中索引的查詢

假設建立複合索引 (姓氏, 名字, 城市)：

  • 條件包含 姓氏（命中第 1 欄）
  • 條件包含 姓氏 + 名字（命中前 2 欄）
  • 條件包含 姓氏 + 名字 + 城市（完整命中）
❌

導致索引失效的查詢

  • 直接查詢 WHERE 名字 = '卿順'（跳過最左邊的姓氏）
  • 直接查詢 WHERE 城市 = '台北'（跳過前兩個欄位）
概念 4 / 4：最左前綴原則 資料來源：wiki/04_composite_index.md
單元五：實戰避坑與總結

索引不是越多越好！三大常見失效地雷

🧮

地雷 1：欄位加函數

寫出 WHERE YEAR(日期) = 2026 會破壞原本排序，導致目錄無法使用。

🔎

地雷 2：前導萬用字元

查詢 LIKE '%關鍵字' 就像不知道字的開頭部首，只能整本重翻。

⚖️

地雷 3：過度建立索引

每次新增或修改資料都要同步更新所有 B+ Tree，索引太多會拖慢寫入速度。

📌 一句話總結：索引是用「額外的儲存空間」與「寫入維護成本」，換取「讀取查詢的極致速度」。建立前先看最常查詢的條件，並把區分度最高的欄位放在複合索引最左邊！
